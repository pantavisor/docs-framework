## Closing summary

- **Surfaces covered**: both in-scope `meta-pantavisor` surfaces. `features` — the 11-token `PANTAVISOR_FEATURES ??=` default in `classes/pvbase.bbclass:2-12`, the 3 tokens advertised in its off-by-default comment block, the 4 `:append`/`:remove` modifiers in `conf/distro/*.inc`, and all 23 distinct tokens that appear in a `bb.utils.contains('PANTAVISOR_FEATURES', …)` gate anywhere in the layer (`*.bb`, `*.bbappend`, `*.bbclass`, `*.inc`, `*.conf`), each cross-checked for whether it is load-bearing. `kas-targets` — 21 files under `kas/build-configs/` (5 top-level + 16 under `release/`), their `target:` fields (3 distinct: `pantavisor-starter`, `pantavisor-remix`, `pantavisor-appengine-distro`) and their filenames, checked against every `kas build …` example in `docs/`.
- **Worst finding**: S1 — six load-bearing feature tokens (`wakelocks`, `console-logging`, `automod`, `caam-nxp`, `dcp`, `debug-hooks`) have zero mention anywhere in `docs/`. `wakelocks` is the sharpest case: the runtime feature it enables is documented at length in the `pantavisor` repo's docs, and `pvbase.bbclass` itself names the token in a comment, but a reader of these docs has no way to learn that `PANTAVISOR_FEATURES:append = " wakelocks"` is what builds it in.
- **What's compliant**: the `PANTAVISOR_FEATURES` default string now matches `pvbase.bbclass` exactly on both pages (`dm-crypt dm-verity autogrow runc tailscale debug rngdaemon pvcontrol xconnect xconnect-dbus-systembus container-mdev`) — the three-way `meta-pantavisor.md` / `build-system.md` / source disagreement from the 2026-08-27 run is resolved, and the two tables are now byte-identical in their token list. The 2026-08-27 S1 (`.github/configs/release/` as the copy-pasteable path in 14 files) is also resolved: every `kas build` example in `docs/` now points at `kas/build-configs/release/`. All three `target:` values are documented in `get-started.md:94-103`'s target table, along with `pantavisor-bsp` and `pantavisor-initramfs`.
